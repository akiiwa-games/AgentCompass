# roll reference

Full mechanics behind `roll`; the SKILL.md default path needs none of this unless a result says otherwise.

Herdr core (`hc`) is a host, not a quota account. It detects the actual `HC_TERMINAL_ID` and launches an owned child terminal. See [Herdr setup, capabilities and return paths](herdr.md) before first use. Cindy's shell exposes no supported parent mailbox, so raw roll there is refused; its plugin lives in the separate `cindy-agentcompass-plugin` repository.

Never manually choose between Paseo `create_agent`, Claude `Agent`, Codex `spawn_agent`, Antigravity `invoke_subagent`, `run_dot_task.py`, or raw CLI. Pass the task inline, from stdin, or as a Markdown file; `--hours <n>` is optional (without it the classifier estimates hours in the same call; the source and confidence are reported under `assumptions`):

```bash
agentcompass roll --task "<text>"          # inline
agentcompass roll --task - < task.md       # stdin, any length
agentcompass roll --brief task.md          # a file
```

`--task` and `--brief` print the same short result: `status`, `next_action`, `worker`, `reason`, pointers (`next_argv`, `worker_output`, `worker_prompt_file`) and `details`, the path of the full result (also saved for every call). `--verbose` prints the full result instead. `agentcompass roll -h` lists only the options of this command; in a source checkout without an install the command is `python -X utf8 <checkout>/agentcompass roll ...` (same arguments).

`next_argv` and `continuation_argv` are ready-to-run commands (an argv list, so a path with spaces needs no quoting) that go through the same public entry: `agentcompass launch ...` for a Paseo dispatch, `agentcompass dot status ...`, `agentcompass grok-bot status ...`, `agentcompass chatgpt-web --prompt ... --out ...`. Run them as given; never swap in a script path.

`roll` automatically detects the caller's host session (`PASEO_AGENT_ID`, Orca's `ORCA_AGENT_SESSION_ID` / `ORCA_TERMINAL_HANDLE`, `ANTIGRAVITY_CONVERSATION_ID`, `CLAUDE_SESSION_ID` / `CLAUDECODE`, `CODEX_THREAD_ID`, `PI_SESSION_ID`, `OPENCODE_SESSION_ID`), classifies the brief, allocates and records the worker, and chooses the best dispatch surface (`paseo`, `dot`, `cli`, `chatgpt-web`, `native`, or `self`). Every dispatch requires a real addressable parent session ID, host, and message address; missing information stops dispatch before classification or launch (`--dry-run` diagnostics remain available).

A Paseo single-use launch claim or a notifier marked `watching` does not confirm that a worker was created. Until a validated host observation binds the worker identity to the dispatch, roll returns `pending` with explicit `next_argv`. Run that command to observe the same dispatch; do not roll again or repeat create. Until then Paseo's `get_agent_status` answers "not found", which is not a failure. After observation confirms the worker, the existing launch/completion notification behavior applies. If Paseo confirms no worker was created, the dispatch ends `create_failed` and `cause` names the fixed failure class and any structured error code (`host_creation_failed:<class>[:<code>]`). Automatic cooldown (`launch_failures`) and fallback (`dispatch_fallback.py`) require positive structured evidence that a create refusal belongs to the candidate (provider, account, or model); a request-scoped (`request_invalid`) or unclassified (`unknown`) create refusal stops the dispatch immediately (`caller_action: "check_error"`) with no cooldown and no candidate walk. Candidate-attributed create refusals, bundles refused at prepare, workers that ended in error, stuck provider retries the bridge stopped, or turns whose provider failed are retried on the same bundle after its backoff when the classifier scoped it `transient` and `--can-wait-hours` allows the wait (nothing blocks meanwhile: the retry is scheduled, `status: pending` with `retry_at`, and the failed attempt's watcher or the next observation of the dispatch starts it once due; the brief counts as dispatched until the retry runs or, if nothing started it within `--can-wait-hours` of the failure, is retired as `retry_expired`; `dispatch --dispatch-action release` on the dispatch cancels a scheduled retry), and otherwise relaunched on the next candidate of a fresh allocation with every failed bundle of the dispatch unavailable. Each attempt is its own registry row linked by `attempt_of` to the dispatch the parent holds; observing that dispatch follows the current attempt; the parent gets one notification when the dispatch reaches a final state, listing the attempts, and `status: blocked`, `cause: no_candidate_left` when nothing is left. A model the owner named (`--model`) is never switched: it is retried only on a transient failure whose backoff fits `--can-wait-hours`, and otherwise the parent is told (`owner_named_model_failed`). `task_input` and worker-own errors (`none`) are not relaunched and are reported as before. `AGENTCOMPASS_ROLL_FALLBACK=off` restores the old behaviour, where `next_action` says rolling again is safe. See [the dispatch lifecycle](dispatch-lifecycle.md) for the states, the one-writer-per-`--workspace` rule (`status: blocked`, `blocked_by`, `--access`), the `warnings` a roll without `--workspace` gets about other writers in its directory, and `--new-worker`.

Selection and launch preflight both check the chosen model's applicable windows on its actual bound quota source. A fresh exhausted five-hour window prevents an immediate dispatch even when weekly capacity remains and the short window has no pricing specification. Explicit `draws` win; otherwise a window's scope is data only ([`window_scope.py`](../scripts/window_scope.py)): the account or plan spec's `windows.<id>.models` (tags matched as whole tokens of the model id) or `models_except`, and a `models` list the provider reports on the reading. A window no source scopes binds every model, so an unknown allowance can stop a launch but is never skipped; no window id or model name is special-cased in code. The Router Gate decides from the same rules (`quota_pools.launch_blockers` on `usage_reading.usage_snapshot`). No capacity or burn rate is invented for an observation-only limit. Fresh recovery or an available alternative account can permit dispatch; missing/stale data retains the existing uncertainty policy rather than becoming a blanket denial.

Do exactly what the short result's `next_action` says. The cases below describe the full result (`details`, or `--verbose`), where `launched`, `dispatch_mode` and `caller_action` give the same answer in detail:
- **`launched: true` (`caller_action: "already_launched_do_not_respawn"`)**: `roll` has **already launched** the worker (`dispatch_mode: "paseo"`, `"cli"`, or `"dot"`). **Do NOT call `create_agent`, `Agent`, `spawn_agent`, or `invoke_subagent` again.** Follow `next`: Paseo registers a bounded local notification watcher (PID, deadline and durable state in `worker.completion_notification`) that sends the parent one finish/error/permission notice containing the worker's final reply. A notice the watcher did not send is delivered once on the next reservation read, roll, or gate call. If no active watcher is confirmed, `worker.continuation_argv` observes the same dispatch. CLI has no automatic callback: the caller must watch `worker.output` / `worker.stderr` and own the process until exit or cancellation. For Dot use `continuation_argv`.
- **`launched: false` and `dispatch_mode: "self"` (`caller_action: "execute_self"`)**: Execute the task directly in your current session; do not spawn a subagent.
- **`status: "blocked"` and `caller_action: "wait_for_reset"` (`start_after_hours`)**: Returned only when the caller passed `--can-wait-hours <h>` and a stronger model whose short quota window resets within `h` hours beat all ready-now substitutes after waiting cost. Nothing was launched; wait `start_after_hours` for the quota window reset, then run `roll` again (or re-run without `--can-wait-hours` to launch the best ready-now substitute immediately). Without `--can-wait-hours`, `roll` never defers and always launches the best model that can start now.
- **`status: "batch"`** (several `--brief`): `results` holds one result per brief, in order, each with its own `status` and `next_action`. Briefs are classified concurrently, then routed and launched one at a time so each allocation sees the reservations before it. Per-brief flags (`--hours`, `--can-wait-hours`, `--task-id`, `--title`, `--local-only`, `--keep-whole`, `--file`, model overrides) are refused; roll such a brief on its own.
- **`launched: false` and `dispatch_mode: "split"` (`caller_action: "roll_each_line"`)**: The classifier read the whole brief and answered `multi_task: true` with a `task_count` (`2`, `3` or `>3`): the brief bundles separate tasks that different workers could do at the same time. Nothing was allocated or launched, and the ledger row (stage `split`) authorizes no launch. The parent stays the coordinator and splits the brief itself: it does the tasks coupled to its conversation, writes one brief per independent task and rolls them together (`--brief a.md --brief b.md`), and starts a task that needs another's result once that result returns. Never hand the tasks to one worker to coordinate. If the brief truly is one assignment, `--keep-whole "<reason>"` sends it to one worker anyway; the ledger keeps the reason and the daily audit lists it.
- **`launched: false` and `status: "scorer_unavailable"` (`caller_action: "parent_autonomous_choice"`)**: All System-One classifiers timed out or failed. Mechanical keyword fallback has been removed so no worker is launched on a keyword guess; the parent session chooses autonomously (`self` or an explicit `--provider <p> --account <a> --model <m> --effort <e> --basis "scorer_unavailable: parent autonomous choice"`).
- **`launched: false` and `dispatch_mode: "native"` (`caller_action: "launch_with_native_host_tool"`)**: Returned when `--parent-host native --parent-id <session-id> --parent-address <inbox-address>` is passed (or when neither Paseo nor a local CLI is available). Pass the **contents** of `worker_prompt_file` to the native host subagent tool using `route.bundle` and preserving the live preamble. Do not switch to Paseo or pass the filename as the prompt.
  - **Orca** (`parent_host: "orca"`, detected from `ORCA_AGENT_SESSION_ID` / `ORCA_TERMINAL_HANDLE`, or `--parent-host orca`): `next` is the `orca orchestration worker-start --spec ... --agent <provider> --model --effort` command for the routed bundle. The parent address is Orca's own mailbox spelling (`orca_session_id:<id>`, or the `structworker_...` handle of a dispatched worker); the worker reports with its injected preamble.
  - **T3 Code** (`parent_host: "t3"`, detected from `T3_MCP_URL` + `T3_MCP_BEARER_TOKEN`, which T3 sets for its Pi provider only, otherwise pass `--parent-host t3` or set `ROUTER_PARENT_HOST=t3`): `next` is the T3 MCP `delegate_task` call (`orchestrator_capabilities` first). T3 addresses the parent thread through the MCP credential and delivers the result itself, so the parent address is the session ID; do not poll `task_status`.

The source brief remains unchanged. The router appends the [worker communication contract](worker-communication.md) and actual parent address to `worker_prompt_file` on every route. `--hours` is optional and positive when given. Follow the returned continuation command for Paseo/Dot; CLI worker PIDs belong to the caller and must be waited for or stopped. The [parent-address gate contract](parent-address-gate.md) describes enforcement and host coverage.

Grok Bot uses the distinct provider/account/model selector `grok-bot` and joins
automatic routing when ready and enabled; no override flags are needed.
Follow [Grok Bot setup and usage](grok-bot.md) for the pinned upstream
CLI and `roll` command. It runs remotely and accepts text; no local file access
or Paseo-native support is implied. The service has independent conservative public
capability priors; its underlying model identity and dollar price remain unknown.
Quota ownership, capacity and local ratings come from effective account configuration.
The channel still excludes local-only, visual, GUI and file-transfer work: the Bot
cannot see images, transfer files, or run on this machine. Shared Grok observations retain their freshness; no separate Bot meter is read. Private material needs outbound authorization.
For uncertain delivery, `launched` is `null` and `caller_action` is
`check_delivery_do_not_resend`: run `continuation_argv`, never submit again.

Optional flags, only when they are facts (`agentcompass roll -h`; internal/diagnostic flags live in `--help-all`):
- `--workspace <dir>`: existing directory this worker writes in and claims exclusively (validated and canonicalized once by core; host IDs such as `wks_...` are not accepted). Automatically implies `local_only` (recording `local_only_reason: "inferred from --workspace <dir>"` in the ledger when `--local-only` is omitted). One writer per canonical directory is enforced across all hosts (`paseo`, `herdr`, `cli`, `orca`, `t3`, `native`); each host adapter places the worker into `<dir>` (`cwd` + matching Paseo `workspaceId` when verified for that exact `cwd`, Herdr `--cwd`, CLI `cwd`, or native instructions + `workspace` output field) and refuses before launch when the surface cannot place `<dir>`. Read-only vs write access is judged by the System-One classifier (`access: "read-only" | "write"`).
- `--hours <n>`: expected active worker-hours (optional; when omitted, the classifier estimates it).
- `--can-wait-hours <h>`: only when the task is not urgent — how many hours it may wait for a stronger model's quota window to reset. Without it, `roll` always launches the best model that can start now.
- `--local-only "<concrete local dependency>"`: keep the work on this machine when no `--workspace` is given (local git/daemon/pytest/hardware/intranet/credentials).
- `--keep-whole "<reason>"`: send a brief the classifier read as several separate tasks to one worker anyway (recorded as alert `kept_whole`).
- `--new-worker` / `--resume <agent_id>`: force a fresh worker or resume a specific idle worker owned by the parent.
- `--file <path>` (repeatable): files Dot needs; Dot's returned files are applied to `--apply-to` (default: cwd). Local workers ignore it.
- `--fast`: prefer Codex fast when quota is plentiful or during a pre-reset sprint (public subscription default: `2.5x`; explicit local calibration is retained). An explicit Claude provider/model override plus `--fast` opts into paid usage credits on supported Opus models; automatic quota/reset routing never enables paid Claude fast. See [fast contracts and verification](fast-modes.md).
- The user named the model/effort in this request: add `--provider <p> --account <a> --model <m> --effort <e> --basis "<exact user quote>"`. `--effort` is optional, and `--model <m>:<e>` also works. Pass any `warnings` in the result on to the user.

Classifier input: the classifier reads the complete task text (never a head/tail view or summary) and the same call returns the hours estimate, the urgency the text itself states, and whether the brief bundles separate tasks (`multi_task`, true/false) with how many (`task_count`: `1`, `2`, `3`, `>3`). Every System-One scorer answers these from the whole text: LLM scorers (`claude_haiku_low`, `codex_terra_low`, `agy_flash_low`, `openai_compatible`) as schema fields and TypeSafe Jev as a `noul` and a `choice` question. Default scorer priority cascades from lightest/fastest to slowest (`jev` when API key is configured -> `claude_haiku_low` -> `codex_terra_low` -> `agy_flash_low`). `--hours` always wins; cost is then computed from hours and real rates/quota. Urgency is reported (compact `assumptions` when high, `details` always) and never changes owner, effort or fast mode; `--fast` or an explicit fast request in the text does. Transport: Claude/Codex scorers use stdin, Jev/OpenAI-compatible use HTTP, and the agy scorer sends a short task on its command line and a long one on stdin (stream-json). If all System-One scorers time out or fail, `roll` returns `status: "scorer_unavailable"` (`caller_action: "parent_autonomous_choice"`) rather than guessing from keywords. If no scorer can take the whole text (agy stdin failure with no fallback, HTTP 413), `roll` returns an `error` with the cause instead of cutting the text. The classification is cached 24 h per exact text + scorer identity + rubric/schema; the route (quota, policy, reservations) is always recomputed live.

Edit the brief freely before rolling. Rolling the same task again while its Paseo dispatch is still live returns that dispatch as `pending` with `next_argv` (no second classification, no second launch). When `launched` is false, `next` says why: a user decision, no fitting worker, or neither Paseo nor a CLI for the routed provider (then start it natively with exactly `route.bundle` and the contents of `worker_prompt_file` as its prompt).
